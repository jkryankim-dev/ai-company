# #8 하위(2) '처리 상태 표시' 지시서 — 완료 조건 확정 (2026-09-22, 김기획)

이빌드 재요청(9/21 스탠드업, 9/14 전사회의 배정 이후 미이행)에 대한 PM 확정 문서.
배정 정본: org/assignments.md #8 행. 이 문서는 그 완료 조건의 전문이다.

## 근거
- 이슈 #8 본문 — 2026-09-22 무인증 REST API로 열람(gh 2.63.2는 읽기도 인증 요구, 실측).
  원문 완료 조건 1·3항(처리 상태 표시·유실 상태 식별)이 이 하위 산출물의 범위.
- feat/8-gateway-persist ce36a50 스캐폴드 테스트(gateway-status.test.mjs) — 목표 동작 정의와 정합.

## 하위(1)과의 경계
하위(1) 유실 방지(합격 2026-09-15)가 lastId 저장을 handle 완료 후로 옮겨, 재기동 시 같은 지시가
재수신되게 만들었다. 하위(2)는 그 재수신·장기 처리 동안 "어디까지 됐는지"를 밖에서 보게 하는 것.
유실 방지 자체·워커 멱등성은 이 범위 밖이다.

## 목적
대표가 "답변이 오지 않는다, 기다려야 하나"를 묻지 않아도 되게 한다. 지시의 처리 상태
(처리 중/완료/실패)를 #대표실에서 보게 하고, handle 크래시·게이트웨이 사망 시 상태 기록만으로
어디까지 처리됐는지 식별 가능하게 한다.

## 완료 조건
1. `drainMessages`가 `status(id, 상태)` 콜백으로 '처리 중' → '완료'/'실패' 전이를 보고한다
   (ce36a50 테스트 3종 전부 green).
2. gateway.mjs가 이 콜백을 #대표실 게시로 연결한다 — `!지시` 접수 시 "처리 중", 종료 시 결과
   알림이 #대표실에 온다. 완료 신호가 결과 say() 단일 경로에 의존하지 않는다(이슈 #8 원문 요건).
3. 상태 전이를 runtime/state 파일에 남겨, 재기동 후 직전 진행 중 지시를 gateway.log 없이
   식별할 수 있다.
4. `status` 콜백을 주지 않는 호출부는 기존 동작을 유지한다(하위호환, ce36a50 테스트 3번째와 동일).

상태 값은 '처리 중' | '완료' | '실패'로 고정한다(ce36a50과 동일). 추가가 필요하면 이 문서를 먼저 고친다.

## 검증 방법
- `node --test runtime/tests/` — gateway-status.test.mjs 3종 포함 전 green 출력
- 실기동 1건: `!지시` 접수 → '처리 중' → '완료'가 #대표실에 순차 게시됨을 runtime/logs/gateway.log로 확인
- 재기동: 처리 중 stop-doore.bat → start-doore.bat 후 직전 지시의 상태가 state 파일·#대표실에서
  식별됨(이슈 #8 본문 검증 방법과 동일 절차)
- 검증자: 최감사(배정표 QA 검증 행, 판정은 산출물 최상단 1행 — ADR 0006)
