## 마찰 1. '제안(지시 대기)'에 채택/기각 판정의 창구·시한이 없다 — 4건 2~4일째 같은 문구 재게시

**무슨 일이 있었나**
- 내 제안(#2~#7 GitHub close 일괄 절차서)이 9/23→9/25 3일 연속 같은 내용으로 재제출됐다
  (2026-09-23·24·25-standup.md 김기획 섹션 — 9/25 보고 본인 표기 "3일째 동일 안").
- 나만이 아니다. 남기록 '미결 안건 칸 신설' 9/22 제출 후 채택 대기 3일째(2026-09-25-standup.md:84),
  오운영 콘솔값 목록 정리 9/24→9/25 재제출(동 73행), 정지표 쿼터 집계 계열 제안 9/22→9/25 반복(동 93행).
  9/24 종합이 "배정 없이 반복 표기만 쌓이는 상태"로 지적했고(2026-09-24-standup.md:106), 9/25 종합은
  "한실장 미채택이 원인, 다음 종합에서 처리"로 넘겼다(2026-09-25-standup.md:120·125).
- 서카피만 3회 재제출을 멈추고 "채택 통보 대기"만 표기 — 개인의 임기응변이지 규칙이 아니다.

**왜 막혔나**
- ADR 0008·0009는 '착수 판정' 기준을 만들었을 뿐 '제안→배정' 전환의 소관과 시한은 어느 문서에도 없다.
  approvals.md는 대표 회신 큐라 사내 채택 사안이 들어가지 못하고, assignments.md는 배정된 일만 받는다.
  제안은 매일 회고 파일 각자 섹션에만 존재하니 다음 날 종합이 그것을 이어받는 구조가 없다.
- 나의 본령(대표 지시를 이슈로 쪼갠다)의 입구가 바로 이 전환이다. 입구가 막히면 이슈 생성 경로
  전체가 막히는데, 9/18 보고 마찰 3이 큐 문제였다면 이번엔 채택 판정 문제다.

**무엇을 바꾸면 되나**
- assignments.md에 '제안 접수' 절을 신설한다(검증 대기 절과 동일 구조): 제안자가 행(안/제출일/예상
  분량)으로 등록하고, 종합자는 다음 스탠드업 종합까지 채택/기각 판정을 내린다(시한 24시간).
  채택 시 종합자가 배정행으로 전환한다. 스탠드업 "오늘" 칸의 제안 재게시는 이 행 인용으로 대체한다.
- 9/25 종합이 "다음 종합에서 처리"를 예고했으므로 이 보고가 상정 문서다. 배정표 관리는 내 권한
  (ADR 0006)이라 절 신설은 보고 제출과 함께 자체 시행 가능하다.

## 마찰 2. GitHub 이슈는 '일이 존재하는 곳'인데 쓰기가 막혀 정본이 파일로 이중화됐다

**무슨 일이 있었나**
- 이슈 8개 전부 GitHub 표기가 `담당:없음`이다(매일 스탠드업 현황 블록 실측). 실제 담당·상태는
  assignments.md에만 존재한다. 사규 2조와 매일 게시하는 현황이 어긋난 채 4주째다.
- 이번 주 내가 직접 부딪힌 지점: gh는 쓰기뿐 아니라 읽기도 인증을 요구해서(9/22 실측,
  org/assignments.md:56-57) #8 본문 확인을 무인증 REST 우회로 해야 했다. 이슈 close는
  approvals#11(쓰기 토큰, 9/21 상신·대표 전용) 대기로 #1~#4가 종료 승인(9/21) 후에도 열려 있고,
  신규 생성도 못 해 서카피 '스토어 개선 2안'은 issues-draft.md 파일 접수로 대체됐다(approvals#8).

**왜 막혔나**
- 사규 2조가 GitHub Issue를 일의 존재 장소로 규정할 때 회사에 이슈 쓰기 권한이 없다는 전제가
  반영되지 않았다. 권한이 없으니 정본이 파일로 내려앉았고 GitHub는 표본(표본조차 stale)이 됐다.
- 매일 종합자·각 직원이 "담당:없음"인 현황을 정정 없이 붙여넣고, 읽는 측은 상태를 파일에서 다시 대조한다.
  두 정본을 대조하는 비용이 매일 8명에게 발생한다.

**무엇을 바꾸면 되나**
- 토큰 공급 전 잠정 상태를 ADR로 명문화한다: "issues-draft.md·assignments.md가 정본, GitHub는
  읽기 전용 미러, close·담당 표기 이관은 approvals#11 해소 시 일괄". 사규 2조에 예외 조항을 단다.
- 스탠드업 현황 블록은 GitHub 덤프 대신 배정 정본 요약(이슈번호·담당·상태)으로 바꾼다. 이는
  회의록 양식 변경이라 채택 판정 대상(마찰 1의 '제안 접수'로 상정).
- #11 자체는 대표 전용이므로 현행 유지 — 주 1회 묶음 재상신에 포함한다.

## 마찰 3. 완료 조건 결측이 착수 시점에야 발견된다 — #8 하위(2), 배정 후 8일 만에 지시서 확정

**무슨 일이 있었나**
- #8 하위(2) '처리 상태 표시'는 9/14 전사회의 배정인데 이슈에 완료 조건이 없었다. 이빌드가 착수
  직전인 9/21 스탠드업에서야 완료 조건 확정을 나에게 재요청했고(2026-09-22-standup.md:27), 지시서는
  9/22에 작성됐다(runtime/docs/issue-8-status-display-spec.md, 커밋 8333020). 이빌드 첫 실행 흔적
  (스캐폴드 ce36a50)도 9/22 — 배정 대비 8일.
- 결측은 하류(착수하는 개발자)가 발견해 위로 올라오는 구조였다. 내가 3항목을 채울 수 있는 유일한
  담당인데 그 사실이 배정 시점에 기록되지 않았다.

**왜 막혔나**
- 사규 3조는 "3항목 없으면 착수하지 않고 되돌린다"인데 '되돌림'의 창구·마감이 정의돼 있지 않다.
  이슈 8개가 sprint-01 배정표에서 assignments.md로 이식될 때 담당·상태만 옮겨지고 3항목 검증은
  수반되지 않았다. ADR 0008은 착수 흔적 요건일 뿐 지시서 완비 여부는 다루지 않는다.
- '검증 대기' 절은 산출물 하류(제출→판정) 흐름은 잡았지만 배정 상류(배정→지시서 완비) 흐름은 비어 있다.

**무엇을 바꾸면 되나**
- assignments.md 각 행에 '완료 조건 위치' 열을 추가한다(이슈 본문/지시서 파일 경로). 비어 있는 행은
  `지시서 대기` 마커를 붙이고, 마커 행은 종합자가 매일 블로커로 게시해 나에게 돌린다 — 결측이
  착수 시점(9/21)이 아니라 배정 익일 발견된다.
- 배정표 양식 변경은 내 권한(ADR 0006)이라 이 보고와 함께 금일 자체 시행한다. 신규 배정 행은
  3항목 위치 확인 후 등록으로 운영 규칙에 적는다.
