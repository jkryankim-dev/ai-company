# 주간 마찰 보고 — 이빌드 (2026-10-02 스프린트 회고)

대상 기간: 2026-09-28 ~ 10-02(#8 하위(2) 구현 제출·QA 판정 주간). 근거는 전부 금일 실측이며
각 항목에 출처를 붙였다.

## 마찰 1. 지시서 '검증 방법'이 실측 없이 작성돼, 완료 조건 4개 중 2개가 실행 불가능했다

**무슨 일이 있었나**
- #8 하위(2) 지시서(9/22 확정) 검증 방법의 테스트 명령 `node --test runtime/tests/`는 Node
  v22.22.1에서 디렉터리가 진입점으로 취급돼 실패했다(10/1 실측, glob 재실행으로 6/6 통과).
  재기동 절차로 적힌 stop·start-doore.bat은 Windows 전용 스크립트라 Linux 본서버에서 실행
  불가, 실제 구동은 systemd doore.service였다 — 전부 10/2 정정으로 확인됨
  (`runtime/docs/issue-8-status-display-spec.md:32-43`).
- 실기동·재기동 검증이 자체 실행 불가 구조(운영 게이트웨이는 main 코드 구동, `!지시` 발신·
  restart root 권한은 대표 전용)라는 사실도 지시서에 없어, 내가 9/30 선언→10/1 실측→10/1 PM
  확인 요청→10/2 회신으로 3일을 써서 입증했다(`2026-10-01-standup.md:48` 블로커 항).

**왜 막혔나**
- 사규 3조는 검증 방법을 "누가/무엇으로 확인하는가"로만 요구하고, 작성 시점에 그 명령을
  실제 환경에서 1회 실행해 보는 절차가 없다. 실행 주체가 대표 전용인 절·본 서버 구동 방식은
  지시서 확정 시점에 실측하지 않으면 작성자가 알 수 없는데, 그 실측을 요구하는 규칙이 없다.
- 오류는 최초 실행자, 즉 착수한 담당자가 발견한다. 발견 시점이 착수 이후라 정정 회신(왕복
  1일+)이 개발 일정 안에 들어온다.

**무엇을 바꾸면 되나**
- 지시서 확정 전 "검증 방법 dry-run 1회"를 사규 3조에 추가한다 — green/red와 무관하게
  "명령이 그 환경에서 실행 자체가 되는지"만 작성자 또는 배정 담당자가 확인.
- 대표 전용 전제(`!지시` 발신, root 권한 restart)가 필요한 절은 검증 방법에 처음부터
  '대표 전용'을 명시해, QA가 즉시 별건 대기로 분리할 수 있게 한다(10/2 정정본 37·43행 형식).

## 마찰 2. QA 합격→main 반영 경로가 2주째 없다 — P1 수정이 합격 후 17일째 배포본에 없다

**무슨 일이 있었나**
- #8 하위(1) 유실 방지는 9/15 QA 합격이다. 금일 실측: main의 `runtime/gateway.mjs` 마지막
  변경은 8/18(88ab075), `feat/8-gateway-persist` diff에 gateway.mjs 35줄이 잔존 — 운영
  게이트웨이는 P1 결함 코드 그대로 구동 중이다.
- 9/25 마찰 1에서 '합격(미병합)' 상태 세분화와 gh 미확보 시 로컬 merge 한시 수단을 제안했고
  9/28 allhands에 재제출했다(`2026-09-28-allhands.md:72`). proposals 큐 실측: 등록된 행은
  #1·#3·#7·#8뿐이고 이 병합 건은 없다 — 9/25 회고에서 나온 제안이 큐로 넘어가지 않고
  소멸했다. PR 게시 수단(gh 쓰기 토큰 approvals#11)도 여전히 대기다(`org/approvals.md:95-96`).

**왜 막혔나**
- 'QA 합격' 다음 상태 전이(병합 주체·수단)가 없다는 점은 9/25과 동일한데, 9/25 이후 생긴
  제안 회수 창구(proposals.md)의 등록이 제3자 세션에 의존한다 — 큐 #7은 박빌드, 큐 #1은
  오운영이 등록했다. 제안자 본인이 등록하는 경로가 없어 누군가 거들지 않으면 회의록 머문
  채 판정 기한도 생기지 않는다.
- 병합은 이 서버에서 배포와 같은 효과(운영 게이트웨이가 main 코드 구동)라 승인 경유가
  맞지만, 승인 상신은 이뤄진 적 없다 — 상신을 누가 하는지도 정의되지 않았다.

**무엇을 바꾸면 되나**
- 제안자 셀프 등록을 proposals 규칙에 추가한다(파일 기록은 회사 자체 가능 분류).
- QA '합격' 판정이 나오는 순간 종합자가 병합·배포 승인 상신 행을 배정표에 추가하는 규칙을
  만든다 — 상신 주체를 지정하지 않으면 하위(2)도 하위(1)과 같은 대기를 반복한다.

## 마찰 3. '부분 통과·별건 대기' 판정에 만료 규칙이 없어, 이슈 종결이 무기한 대표 회신 의존이 된다

**무슨 일이 있었나**
- 10/2 최감사 판정: #8 하위(2) "통과(코드·단위테스트 범위) — 실기동·재기동 별건 대기"
  (`projects/beads-sort/qa-log.md:59`). 별건의 전제는 대표 전용 2건(main 반영 승인, `!지시`
  발신 및 restart)이고, "그 전까지 부분 통과(실기동 미확인)" 상태로 배정표에 남는다
  (qa-log.md:76).
- 대표 전용 대기의 재상신은 주 1회 묶음뿐이고(사규 6조·ADR 0011), 별건 대기 자체에는
  상한·만료·재분류 규칙이 없다. 즉 이슈 #8의 종결 시점을 회사 어느 역할도 움직일 수 없다.

**왜 막혔나**
- ADR 0007의 무회신 48시간 기본 동작은 '상신 항목' 기준이다. QA 판정에서 갈라나온 '별건
  대기'는 상신이 아니라서 무회신 규칙이 적용되지 않고, 그대로 종결 없는 보류가 된다.
- 'P1 결함이 운영 중 + 수정본은 판정 완료·배포 보류'라는 상태가 묵시적으로 지속되는데,
  이 지속을 회사가 명시적으로 선택·기록하는 절차가 없다.

**무엇을 바꾸면 되나**
- qa-log 판정에 별건 대기를 만들 때 전제 목록(대표 전용 항목별)과 대기 상한(예: 2주)을
  함께 기재한다. 상한 경과 시 종합자가 주 1회 묶음 재상신에 'P1 미배포 지속 승인' 항목으로
  올려 계류 여부 판정을 받는다 — 무회신이면 ADR 0007대로 대기로 기록하고, 적어도 상태가
  판정된 만료로 전환된다.
