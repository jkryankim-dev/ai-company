마찰 1은 '요청 쪽' 회신 창구 통합만 다룬다).

## 마찰 1. 콘솔값 회신 창구가 3벌이다 — approvals#1·#7·console-input.md가 같은 데이터를 따로 요구한다

**무슨 일이 있었나**
- 같은 플레이 콘솔 데이터를 요구하는 항목이 3곳에 나뉘어 있다: approvals#1(명단·최근실행일·D0,
  8/19 상신 — approvals.md:19, 표 기재 29일·9/17 갱신, 재계산 37일), approvals#7(8/20 이후 콘솔
  실측값, 8/26 상신 — approvals.md:25), 전용 창구 console-input.md(9/8 신설 — :4).
- console-input.md:6이 "#1·#7의 회신 창구를 겸한다"고 스스로 적지만 approvals 표 두 행에는 이
  연결이 없다. 9/25 종합 블로커 목록도 #1·#7을 여전히 별도 항목으로 인용한다
  (2026-09-25-standup.md:117).
- 결과: 창구는 17일 무입력(console-input.md:21, 9/8 이후 무변경), 내 #3 산출물은 5주째 갱신 불가 —
  추적표 "개별 명단은 콘솔값 대표 입력 대기 — 표는 미갱신"(tester-tracker.md:12), 일지 '옵트인
  현황 변화' 칸은 8/20 이후 전부 "—"(test-journal.md 일지).

**왜 막혔나**
- 창구를 늘리면서 기존 두 행을 정리하지 않았다. 요청 단위가 '값'(콘솔 화면)이 아니라 '사건'(지시
  003, '8/20 이후 실측')이라, 같은 화면 붙여넣기 1회로 끝날 회신이 3곳으로 흩어졌다.
- 회신 동작과 종결 동작이 연결돼 있지 않다. 대표가 console-input.md에 값을 넣어도 approvals#1·#7
  행은 '대기'로 남아 별도 종결이 필요하고, 반대로 회신되면 당번은 표 2행과 창구를 동시에 갱신해야
  한다.

**무엇을 바꾸면 되나**
- approvals#1·#7을 console-input.md를 가리키는 단일 행으로 병합한다(값 제공은 대표 전용 유지 —
  ADR 0011). "동일 사안 재상신 금지, 한 행의 대기만 인용" 전례(approvals.md:46)를 행 병합으로
  확장하는 것이다.
- 종결 조건을 "console-input.md 입력 = 관련 approvals 행 전부 처리(날짜)"로 못박는다. 기록 관리
  사항이라 approvals.md:9 선례로 회고 확정 가능하다.

## 마찰 2. 종료 처리된 이슈의 '대표 확인 필요' 항목이 어느 큐에도 없다 — #7 §4 4건

**무슨 일이 있었나**
- #7은 9/21 종료 처리 승인받았다(assignments.md:17). 산출물 §4에는 대표 확인 4건이 남아 있다:
  방침 URL 콘솔 등록 여부(policy-kit.md:63, context.md:36 "별도 미확인"), 콘텐츠 등급 설문 제출
  여부(:64, context.md:38 미확인), 데이터 안전 양식 제출 여부(:65, context.md:37 미확인), 코인
  획득 경로가 광고 보상 단독인지(:66).
- 4건의 대기처가 제각각이다: 설문·양식 2건은 approvals#7 괄호의 '양식 제출 여부'로 간접 포함,
  URL 등록 여부는 어느 행에도 없다, 코인 경로는 APP_REPO(approvals#2) 의존. #7이 닫히면서 적어도
  URL 등록·코인 경로 2건은 발행 주체도 대기 큐도 없는 상태가 됐다.
- 대조: #6-카피의 광고 ID 답항은 배정표 행 자체에 '#6-기술 확정 대기'로 남아 추적된다
  (assignments.md:16). 닫는 방식의 차이가 미결 항목의 존재 여부를 결정했다.

**왜 막혔나**
- 종료 판정 기준이 '산출물 완비'(approvals#5 판정, approvals.md:82-89)인데 '대표 확인 필요' 마커는
  산출물 완비와 양립한다. 종료 처리 절차에 확인 필요 항목의 이관 단계가 없다.
- 사규 2조 "이슈에 없는 일은 존재하지 않는 일"이 역방향으로 작동한다 — 이슈가 닫히면 그 내부의
  미결도 목록에서 사라진다.

**무엇을 바꾸면 되나**
- 종료 판정 절차에 1줄: 산출물 내 '대표 확인 필요' 마커는 종료 처리 시 approvals 행으로 이관한다
  (당번 = 산출물 작성자). §4 4건을 소급 등록하며, 마찰 1의 병합 행에 얹는다.

## 마찰 3. 마감 시계가 스탠드업 개최에 연동돼 주말에 회사 기한이 정지한다

**무슨 일이 있었나**
- 기한 표현이 전부 스탠드업 기준이다: '제출 익일 스탠드업까지, 상한 48시간'(assignments.md:29),
  '대기 일수는 매 스탠드업 종합 시점 갱신'(approvals.md:14), ADR 0011 자체진행 마감 '익일
  스탠드업(9/19)'.
- 9/19는 토요일이라 스탠드업이 없었다. 9/21 갱신 로그 3건이 전부 주말 경과를 자체 기록했다 —
  "마감(9/19 스탠드업)은 주말·부재로 금일 실행"(approvals.md:81·89, assignments.md:49·52),
  "마감(9/19) 2일 초과"(approvals.md:95, assignments.md:55).
- 검증 대기 첫 건도 같은 구조였다: 9/15 제출 → 상한 도래 9/17 → 판정 9/21(6일,
  assignments.md:34). '초과 시 종합자가 블로커로 게시' 규칙(assignments.md:29)이 발동한 기록은
  9/18·9/21 회의록에서 확인되지 않는다.

**왜 막혔나**
- 기한의 시계가 달력이 아니라 회의 개최다. 스탠드업이 없는 날(주 2일)에는 기한 도래를 감지·집계하는
  주체가 존재하지 않고, 초과 규칙도 '종합자가 게시' 대상이라 스탠드업 부재 시 발동 자체가 불가능하다.

**무엇을 바꾸면 되나**
- 기한을 달력 일자로 통일한다(예: '제출+2일 09:00', '상신+N일'). 스탠드업은 보고 창구일 뿐 기한의
  시계가 아님을 운영 규칙에 명시한다.
- 스탠드업 없는 날 기한이 도래한 항목은 다음 영업일 종합에 '초과(N일)'로 명시 집계한다 — 주말이
  자동 사면으로 기능하지 않게 한다.
