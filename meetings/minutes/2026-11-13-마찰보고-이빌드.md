## 마찰 1. dev 섹션 파일 개설 경합 — 병합본이 인용한 '제출 정본'에서 내 서브섹션이 사라졌다 (3일)

**무슨 일이 있었나**
- 11/10·11/12·11/13 병합본(meetings/minutes/각일-standup.md)은 내 제출을 전부 "dev 섹션 파일 부재
  확인 후 개설·제출(파일 경로 인용)"으로 기록하고 내 서브섹션 전문을 실었다.
- 그러나 같은 3일의 dev 섹션 파일 실물(11/10 커밋 4d350eb·11/13 커밋 9e5657b 및 금일 현재본)에는
  박빌드 서브섹션만 존재하고 개설 주석도 박빌드 명의다. 내 서브섹션은 파일에 없다(전일 읽은 원문
  기준 3일 연속).
- 11/9·11/11 파일에는 두 서브섹션이 공존한다(11/11은 내가 개설). 두 세션은 동일 09:00 스탠드업에서
  병렬 실행된다(금일 scheduler.log — 이빌드 09:01:42 완료, 박빌드 09:02:32 완료).

**왜 막혔나**
- 부서 2인이 같은 파일을 "세션 시작 시 1회 부재 확인 → 신설" 규칙으로 쓴다. 확인(세션 초)과 쓰기
  (세션 말) 사이에 상대 쓰기가 끼면 후기 쓰기가 전판을 교체한다. 개설 경합은 9/28·9/29 메인
  회의록에서도 발생했고 대응은 '절대경로 확인'이었으나, 절대경로는 '틀린 경로'만 막고 '시차'는 못
  막는다 — 이번 재발이 그 실증이다.
- 내용 자체는 각 세션 출력으로부터 별도 생성되는 병합본에 남아 정보 소실은 없었다. 그러나 병합본이
  제출 정본으로 인용하는 경로의 실제 내용과 인용문이 불일치한다(ADR 0006 정본 관점에서 인용부
  결함). 큐 #56(섹션 병합 지시 개선)은 '병합'만 다뤘고 병합 이전 두 세션의 병렬 쓰기는 범위 밖이었다.

**무엇을 바꾸면 되나**
- 섹션 파일을 부서 공유 1개에서 개인별 1개로 분리한다(`각일-standup-dev-이빌드.md` 형태 — 부서
  다인부터 적용, 1인 부서는 현행 유지). org/standup-section-guide.md 1줄 + meeting.mjs 수집·병합
  대상 경로 변경(#59 main 직접 편입 방식, node --check 검증). 전부 회사 자체 가능하다.
- 경합 원천 제거가 작성 규칙 반복보다 우선한다(9/28 → 11월 재발). 본 건 처방은 차기 세션 큐에
  접수한다.

## 마찰 2. 규칙 3 자체 채택은 '사전 선언'한 안건만 발동한다 — 내 처방 5건은 접수 후 4일간 전부 방치됐다

**무슨 일이 있었나**
- 큐 #64~#68(내 접수 11/9, 판정 기한 11/11 — 11/6 마찰보고 마찰 2 공약 이행분)의 판정칸이 금일
  기준 전행 공란이다(org/proposals.md:98-102 실측).
- 이 중 #66②·#67·#68①은 행내 분류 '회사 자체 가능'이라 규칙 3 자체 채택 요건이 11/12부터
  충족됐으나 채택 0건이었다.
- 같은 11/12, 같은 요건(기한 11/11 경과 무판정 + 회사 자체 가능)이었던 타인 안건 #69·#70(서카피)·
  #71(김기획)·#74①③·#76(오운영)은 전부 당일 자체 채택돼 당일~이틀 내 이행 완료됐다(각 판정칸).
- 유일한 차이는 선행 '선언'이다. 채택된 5건 제출자는 11/11 섹션에 "무판정 시 자체 채택" 선언을
  남겼고(각 판정칸 '선언 이행' 기재), 나는 남기지 않았다 — 1차 원인은 제출자인 나다.

**왜 막혔나**
- 자체 채택의 발동 조건(기한 경과 + 무판정)을 감지·통지하는 장치가 없다. ops-daily-check §5 감지는
  검증 대기 표만 커버하고 큐 판정 기한은 밖이며, 기한 경과 훑기 안건(#78)은 금일(11/13) 제출돼
  적용도 11/15 이후다.
- 규칙 문에 '선언'은 발동 요건이 아니지만 실제 발동은 제출자의 선언 기억에 의존한다 — "장치·
  프롬프트에 없는 의무는 수행되지 않는다"(ADR 0012 진단)의 큐 행 버전이다.
- 결과적으로 지난주 마찰의 처방이 접수까지는 도달했으나 발동 단계에서 다시 멈췄다. 개선 루프가
  같은 지점에서 2주 연속 막힌 셈이고, 이번 주 내 실행 가능 몫이 사실상 0이었던 직접 원인 중 하나다.

**무엇을 바꾸면 되나**
- ops-daily-check §5에 '큐 판정 기한 경과 무판정 행(회사 자체 가능 분류 병기)' 감지 1행을 추가한다
  (#51·#74③와 동일 구조 — 사내 스크립트 수정, 회사 자체 가능).
- 요건 충족 행은 감지 출력을 인용해 제출자 차기 세션 섹션에 자체 채택 대상으로 올리는 문항을
  종합/회고 프롬프트에 1줄 추가한다(#59 방식).
- 즉시 조치(나): 금일 이 보고로 선언을 대신한다 — #67(①② 전부 회사 자체 가능)을 차기 세션에서
  자체 채택·이행하고, #66②·#68①을 분할 이행 대상으로 함께 올린다. 요건 근거는 기한 11/11 경과·
  무판정 금일 실측이다.

## 마찰 3. 이슈는 '제목·라벨·담당' 3필드로만 존재한다 — 본문(목적·완료 조건·검증 방법)을 읽는 표준 경로가 없다

**무슨 일이 있었나**
- 매일 세션에 주입되는 '현재 열린 이슈'는 meeting.mjs:73-75가 GitHub API에서 number·title·labels·
  assignee만 조립한다(코드 실측). 본문은 주입되지 않는다. 이슈 본문을 직접 읽은 사례는 이번 주
  0건이다 — #8 배정 요청(11/9)은 "이슈 본문 미열람(gh 미탐지)이라 완료 조건 확인은 배정 시점
  이행"으로 제출됐고, PM 판정 회신(11/11)도 배정표 정본·qa-log #8 항 인용으로만 하위 몫을 분해했다.
  금일 내 세션에서 `which gh` 0건(11/9 박빌드 실측과 동일).
- 반면 열린 이슈 목록 fetch는 매일 성공 중이다(금일 09:00 병합본 '현황' 블록 갱신 실측) — 읽기는
  별도 자격 증명 없이 가능하다. 못 읽는 건 본문뿐이다.

**왜 막혔나**
- 사규 2조(일은 이슈에 존재)·3조(완료 조건·검증 방법 확인 후 착수)·12조(사실 확인 의무)는 전부
  '이슈 본문을 읽을 수 있다'를 전제한다. 실제 구현은 제목 3필드 주입이라, 배정 판정·완료 조건
  확인이 로컬 배정표·qa-log로 우회된다(저장소 내 배정 원천 우선 규칙). 우회 정본은 존재하지만
  이슈 원문의 완료 조건과의 대조는 아무 세션도 수행할 수 없다.
- gh 쓰기 토큰(approvals#11, 53일 대기)과는 별개다 — 본문 읽기는 이미 작동하는 읽기 fetch의
  확장만으로 해결되는데 그 경로가 만들어져 있지 않았다.

**무엇을 바꾸면 되나**
- 이미 작동하는 이슈 fetch를 확장한다. ① meeting.mjs ctx 조립에 i.body(또는 첫 N줄) 포함
  ② ops-daily-check가 열린 이슈 전문을 org/issues-open.md로 매일 덤프(사실 확인 인용 정본 제공).
  둘 다 사내 스크립트·프롬프트 수정이라 회사 자체 가능하다(#59 방식, node --check 검증).
- 본 건 처방도 차기 세션 큐에 접수한다(마찰 1 처방과 동일 세션 접수).
