# 주간 마찰 보고 — 오운영 (2026-10-23)

대상 기간: 2026-10-19 ~ 10-23 (직전 보고: 10/16 마찰보고). 근거는 저장소 실측이며 각 항목에 출처를
붙였다. 커밋은 자동 저장에 맡긴다(9/21 이래 방식).

동일 제출분과의 중복 확인: 금일 시점 타 직원 10/23 마찰보고는 미접수(meetings/minutes/ 디렉터리
실측). 과거 보고와의 층위 구분: 10/16 마찰 1(채택~구현 사이 임시 운영 부재)·마찰 2(주간결과 제안의
큐 미등록 표류)·마찰 3(대표 전용 무회신의 출구 부재)과는 안건을 달리한다(각 항목에 명시). 10/16
마찰 3(approvals#12 무회신)은 이번 주 상태 변화(승인 요청 상정·큐 #33 채택)만 있고 병목 구조가
동일해 이번 보고에서 다루지 않는다(반복 회피).

## 마찰 1. 채택 판정이 이행 배정으로 연결되지 않는다 — 10/23 "무판정" 사실오기로 발각, 발각 전까지 탐지 수단 없음

**무슨 일이 있었나**
- 10/21 종합은 금일 기한 제안 판정에서 #31·#36~#39만 판정하고 #32~#35(기한 10/21)를 상정하지
  않았다(2026-10-21-standup.md:141-146 — 해당 절에 #32~#35 없음).
- 10/22 종합이 #32·#33을 채택하며 "이행: 오운영"을 명시(2026-10-22-standup.md:107-109). 판정칸도
  10/22 09:15 자동 저장(fbf0f7a)에 반영 완료(10/22 09:10판 0b6da40은 아직 무판정 — git 실측).
- 그런데 10/23 내 스탠드업은 "큐 #32·#33(내 접수분)은 무판정 — 판정은 종합자 몫"으로 기재
  (2026-10-23-standup-ops.md:19, 병합본 :74 "대기 항목"에도 동일). 채택 다음 날 세션에서 확정
  판정을 읽지 않은 사실오기다. "오늘:" 칸에 #32·#33 이행 계획도 없었다.
- 발각은 남기록의 부가 실측(2026-10-23-standup.md:92①·:381)이었고 종합은 "사실오기, 재작업 아님.
  확인 요청"(:124). 이 보고가 그 확인 요청에 대한 정정 기록을 겸한다 — 규정된 정정 기재 창구는
  없다(마찰 원인 4와 동일 구조).

**왜 막혔나**
- 채택·이행 지시의 정본은 전일 종합 회의록과 큐 판정칸뿐인데, 제출자가 그것을 확인하는 단계가
  어디에도 없다. 내 일일 루틴(ops-daily-check)은 inbox·console·REST 실측뿐이라 판정 확인은
  세션마다 자발에 맡겨진 상태다.
- "이행: 오운영" 지시가 배정표 행으로 이어지는 절차가 없다. 배정표에 #32·#33 이행 행은 부재
  (오운영 명의 행 전수 grep — #1·#11·#12 이행행만 존재). ADR 0008은 배정 근거를 배정표 행으로
  요구하므로, 채택 지시만으로는 착수 근거가 성립하지 않는다. #34(김기획)는 채택 다음날 이행하며
  스스로 반나절 행을 만들어 해결 — 개인 성실도로 버티는 구조다(#22 최감사 8일 지연과 동일).
- 판정칸 전사 주체가 행마다 제각각이다. #25~#31·#36~#39는 "제출자 전사" 문구가 붙고
  #32~#35·#40은 전사 문구 없이 기입돼, 읽는 시점에 그 행이 확정 판정인지 대기 중인지 구분 근거가
  없다.
- 부수로 규칙 3(기한 경과 무판정 시 자체 채택)의 발동 경계도 불명확하다. 10/21 종합 미상정 시점에
  제출자인 나는 자체 채택할지 하루 더 기다릴지 판단 근거가 없었고 실제로는 하루 늦은 종합이
  판정했다. 기다림이 정답이 된 순간에도 그것을 알 방법이 없다.

**무엇을 바꾸면 되나**
- 종합자의 큐 판정 출력에 배정표 이행 반나절 행(담당·기한) 등록을 1세트로 묶는다(큐 #15 "정본
  반영 1세트"와 동일 구조의 확장). 최소한 판정칸에 이행 기한을 명시한다.
- 제출자 일일 세션 첫 단계에 '전일 판정·이행 지시 확인' 1행을 넣는다. 나는 #32 이행(4번째 점검
  항목)과 병행해 ops-daily-check에 추가해도 되는 몫이라 자체 반영 가능하다(제안, 지시 대기).
- 사실오기 정정은 다음날 자기 섹션에 '정정(대상 문구·정정 내용)' 표기로 남기는 규칙 1줄을
  스탠드업 가이드에 추가한다(제안, 지시 대기).

## 마찰 2. 채택된 규칙의 main 미반영 기간에 '이행 완료' 표기가 먼저 확정된다 — 10/19 판정칸 공백 재발, 감지는 매번 수동 git 대조

**무슨 일이 있었나**
- 10/19 내 부가확인: 10/16 종합이 #25·#26 채택을 선언했으나 판정칸이 공백인 것을 발견, 원인을
  "판정칸 동일 세션 기입 지시(큐 #21②)는 feat/retro-b-digest-writeback(a7dadc0)에만 있고 main
  미병합"으로 특정(2026-10-19-standup-ops.md:16). 금일 재실측으로 a7dadc0은 여전히 main 미포함
  (git branch --contains — feat 브랜치 전용).
- 이 감지·진단에 main HEAD(1235c53)와 feat 커밋의 수동 대조가 필요했다. 10/20 제출자 전사로
  증상은 해소됐으나(2026-10-20-standup-ops.md:15) 원인(main 미반영)은 그대로다.
- 같은 상태의 채택 규칙이 여럿 쌓여 있다: #23 '이행 완료(10-21 검증 통과 — main 병합·재기동은
  대표 대기)', #35 '이행 완료(10-23 — main 병합·반영은 대표 전용 대기)'(org/proposals.md 각 행).
  main 반영 전까지 결함 재발 가능성은 열려 있고, 재발 여부 확인은 매번 개인 수동 실측에 의존한다.

**왜 막혔나**
- 10/16 마찰 1은 "채택~구현 사이 임시 운영 부재"였다면 이번은 그 다음 단계 결함이다 — 구현·검증이
  끝나 '이행 완료'로 표기됐음에도 운영(main 세션)에 규칙이 없어 부작동이 지속되고, 완료 표기가
  반영 상태를 구분하지 않는다.
- 배포(병합·재기동)는 대표 전용이라 반영 시점을 회사가 통제할 수 없는데, 그 대기 기간의 운영
  경로(수동 전사·수동 병합)를 상태로 표기하는 규칙이 없다. 결국 "규칙이 있는가"와 "규칙이 작동하는가"가
  배정표·큐 기록에서 동일한 '완료'로 보인다.

**무엇을 바꾸면 되나**
- 채택 이행의 완료 표기를 2단계로 분리한다: '이행 완료(운영 반영)' / '이행 완료(main 미반영 — 수동
  경로: 전사 등)'. 편입칸 표기 규칙 1줄이면 족하다(제안, 지시 대기).
- main 미반영 잔여 채택 규칙은 주 1회 묶음 재상신(큐 #17 규칙 준용) 항목에 포함해 반영 대기
  목록이 상시 가시화되게 한다(제안, 지시 대기).
