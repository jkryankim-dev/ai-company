# 스프린트 01 — 비공개 테스트 2주 (2026-08-18 ~ 09-01)

테스터는 모였다. 이제 이 2주의 목적은 기다리는 것이 아니라 두 가지를 만들어내는 것이다.

## 목표 A. 프로덕션 심사를 한 번에 통과할 기록
구글은 머릿수가 아니라 참여와 대응의 기록을 본다. 2주 뒤 신청서 10문항(각 300자)에
"어떤 버그를 발견했고, 어떻게 고쳤고, 빌드 몇에서 재배포했는지"를 채워 넣을 실제 기록이 필요하다.

- **test-journal.md 를 매일 갱신한다** (날짜 / 빌드 / 보고된 문제 / 원인 / 수정 커밋 / 재배포)
- 사전 출시 보고서(Pre-launch report) 크래시는 발견 즉시 이슈화 — 방치가 단독 거절 사유다
- 옵트인 인원 매일 확인 — 12명 밑으로 내려가면 시계는 유지되나 기록이 약해진다. 즉시 대표에게 보고
- 데이터 안전 양식·개인정보처리방침·콘텐츠 등급: 심사 제출물 초안을 2주 안에 완성 (제출은 대표)

## 목표 B. 출시 직후 내놓을 다음 버전 연구
출시일에 1.0이 나가는 순간 다음 카드가 준비돼 있어야 한다.

- 테스터 피드백 수집·분류 → 개선 후보를 이슈로 (근거 없는 기능 추가 금지, 피드백에 출처를 남길 것)
- 경쟁 앱 연구: 같은 장르(워터 소트) 상위 앱들의 리텐션 장치·수익화 구조·리뷰 불만점 분석
- R8 재도전 검증: keep rules 작성 후 축소 빌드가 실기기에서 도는지 확인 (v1.1 후보)
- 스토어 A/B 후보: 스크린샷·설명문 개선안 2안

## 역할
- 김기획: 위 전부를 이슈 트리로. 매일 저널 갱신 책임
- 이빌드: 크래시 대응 + R8 검증
- 박빌드: 심사 제출물(데이터 안전·등급 설문) 초안 + 빌드 파이프라인
- 서카피: 테스터 리마인드 메시지(주 2회분) + 스토어 개선 2안
- 오운영: 옵트인 현황 추적표, 이탈 감지 시 즉시 보고
- 정지표: 테스트 지표 정의(참여율·이탈 지점) 및 주간 집계
- 최감사: 신청서 초안 전수 검증 — 저널 기록과 대조해 지어낸 내용이 없는지
