# 0002. 첫 제품은 두레 사내 대시보드

상태: Accepted
날짜: 2026-08-17
결정자: 대표

## 맥락
개소 첫날 브리핑에서 비서실장이 "만들 제품이 정해지지 않아 PM·개발·마케팅 3직무가 동시에 대기 중"이라고 판정했다.
회사는 신규 창업이라 인수할 기존 업무나 기존 코드베이스가 없다. `develop/flutter`는 Flutter SDK이며 앱 프로젝트가 아니다.
따라서 첫 제품은 (1) 외부 고객 리스크가 없고 (2) 만드는 즉시 회사 자신에게 쓸모가 있으며 (3) 실패해도 되돌릴 수 있는 것이어야 한다.

## 결정
첫 제품은 **두레 사내 대시보드**로 한다. 대표가 한 화면에서 회사 상태를 파악하는 도구다.

### v0.1 범위 (이것만 한다)
1. 직원 9명의 오늘 상태 — 응답 성공/실패, 마지막 활동 시각
2. z.ai 주간 쿼터 소진율 — 남은 노동력을 눈으로 보기
3. GitHub 이슈 현황 — 열림 / 진행 / 완료 개수와 리드타임
4. 승인 대기 목록 — `#대표실`에 올라온 미처리 건
5. 최근 회의록 5건 링크

### 기술 방향
- 데이터 공급: 로컬 Node가 `runtime/state/`, `meetings/`, GitHub API를 읽어 JSON으로 내보낸다
- 화면: Flutter Web. 이유는 같은 코드로 모바일 앱까지 확장해 대표가 폰에서 회사를 볼 수 있게 하기 위함이다
- 배포 없음. 로컬에서만 뜬다. 외부 노출은 v0.1 범위 밖이다

## 하지 않을 것
- 인증·로그인 (사용자가 대표 1명뿐이다)
- 실시간 갱신 (새로고침으로 충분하다)
- 디자인 시스템, 다크모드, 애니메이션
- 외부 배포, 도메인, 호스팅

## 인력 배치
- 김기획: 위 5개 항목을 반나절 단위 이슈로 분해
- 이빌드: 데이터 공급 계층 (Node JSON API)
- 박빌드: Flutter Web 화면 + 저장소·CI 스켈레톤
- 최감사: 완료 판정. 검증 기준은 "빈 PR에 CI 초록" + 각 이슈의 완료 조건
- 오운영: 인수할 반복 업무가 없으므로 이번 제품의 **운영 관점 요구사항**(무엇이 고장났을 때 대시보드에 보여야 하는가)만 담당한다
- 서카피: 대기. 알릴 제품이 아직 없다 (0001 브리핑의 판단 유지)
- 정지표: 3번 항목의 지표 정의를 김기획에게 제공

## 근거
- 대안 A) 새 소비자용 Flutter 앱 → 시장 검증 없이 시작하면 회사의 첫 산출물이 검증 불가능한 것이 된다. 기각.
- 대안 B) 백오피스 자동화 → 신규 창업이라 자동화할 반복 업무가 아직 존재하지 않는다. 기각.
- 채택안은 회사가 자기 자신을 첫 사용자로 삼는다. 요구사항이 명확하고, 쓰는 사람이 바로 옆에 있고, 틀리면 즉시 안다.

## 결과
- 얻는 것: 검증 가능한 첫 산출물, 회사 운영 가시성, Flutter+CI 파이프라인 실전 검증
- 포기하는 것: 이번 분기 외부 매출 가능성
- 재검토 시점: v0.1 완료 후. 그때 외부 제품으로 넘어갈지 결정한다.
